# AssetOps — Facility & Maintenance Management SaaS

**Document type:** Implementation-ready product requirements document (PRD)  
**Version:** 1.0 · 20 November 2026  
**Delivery target:** Working MVP (see docs/planning/roadmap.md for phased estimates).  
**Primary delivery:** A polished, fully functioning local web application with seeded sample data and automated tests.

## 1. Product brief

AssetOps is a multi-tenant computerized maintenance management system (CMMS) for small hotels, clinics, gyms, schools, and multi-location businesses. It replaces spreadsheets and fragmented messages with an asset registry, corrective and preventive maintenance, technician workflows, parts inventory, repair approvals, SLA tracking, and operational reports.

**One-sentence promise:** Know what is broken, who is fixing it, which parts were used, what it cost, and which assets are repeatedly failing.

**Initial buyer:** Owner/operator or facilities manager of a company with 1–10 sites and 50–1,000 maintainable assets.  
**Market validation reference:** MaintainX is an established commercial CMMS; this is a category comparison, not a claim that AssetOps will achieve similar revenue.  
**Proposed pricing hypothesis (not validated):** $49 per location per month for the base plan, with a higher tier for multiple sites and reporting.

### Product outcomes

1. Staff can create a maintenance request in under two minutes.
2. Facility managers can assign and prioritize work without external messaging.
3. Technicians can execute a job and document its work and cost.
4. The asset history reflects all completed work and parts consumption.
5. Managers can schedule preventative work and identify overdue or repeat failures.
6. One organization's users cannot access another organization's records.

### Non-goals for this MVP

No native mobile app, offline-sync mobile client, barcode hardware integration, IoT feeds, public email/SMS sending, third-party SSO, payment processing, vendor marketplace, predictive analytics, compliance certification, or external API dependencies.

## 2. Hard sandbox constraints and implementation contract

The project must function on a Linux desktop with **Node.js 22**, npm packages from a potentially limited mirror, locally available **PostgreSQL / MariaDB / SQLite**, Chrome, and Playwright. The machine has **no general internet**, no Docker, no GPU, no `apt-get`, no CDN access and no paid/external API calls at runtime.

- Prefer **React + Vite** for the UI and **Node.js + Express** for the API. Use plain CSS or a locally installed styling library; no hosted fonts/icons.
- Use **PostgreSQL + `pg`** as the default persistence layer, starting the existing local database service manually. If unavailable, offer a documented local SQLite fallback, using only packages confirmed available in the mirror. Do not silently substitute browser localStorage for a database.
- Keep browser and server on `localhost`. Configure Vite to proxy `/api` and `/uploads` to the backend.
- Password authentication is local; use a vetted password hashing library if available or Node `crypto.scrypt` with a unique random salt, constant-time verification, and secure session handling. Sessions are server-managed; use HTTP-only, SameSite cookies and CSRF protection for state-changing actions.
- Use local disk for attachments with generated filenames, MIME allowlists, limits, and path traversal protection. Store only file metadata and references in SQL.
- Notifications are **in-app only**. Scheduled work is generated by a local worker process or an idempotent server-side tick; no external cron service required.
- Playwright tests run against the actual application and local SQL database. Package installation must not depend on the public npm registry.
- Provide `README.md`, `package.json`, `.env.example`, seed/migration scripts, and straightforward startup commands. No Dockerfiles required.
- Any dependency unavailable in the mirror must be replaced with a standard-library implementation or a documented supported alternative; core workflows must not become placeholders.

## 3. Actors and access control

| Role               | Allowed actions                                                                | Important restrictions                                                         |
| ------------------ | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Organization Admin | Manage organization, users, sites, settings, all reports                       | Cannot access another organization                                             |
| Facility Manager   | Manage assets, work orders, schedules, inventory, approvals, reporting         | Cannot change organization ownership/security settings                         |
| Technician         | View assigned work; update status, checklist, time and evidence; request parts | Cannot self-approve expensive requests or edit costs after closure             |
| Requester          | Create requests, see own requests, comment, confirm resolution                 | Cannot see confidential inventory pricing or other requesters' work by default |

A user can belong to more than one organization; every authenticated request resolves an active organization membership. Permissions are enforced by the API, not merely hidden UI elements. All tenancy-bearing records have an `organization_id`; the server validates foreign keys belong to the same organization.

## 5. Functional requirements

### FR-01 — Organization, facilities, and areas (P0)

- CRUD for organization-scoped facilities; each facility has code, name, address text, timezone and active flag.
- Nested location hierarchy: site → building → floor/area (up to three levels for MVP).
- Site deletion is soft-delete and prevented when active assets/work orders reference it.
- User's site access is limited to explicitly granted sites unless they are organization admin.

### FR-02 — Asset registry (P0)

- Each asset has a unique organization-scoped asset code, name, type/category, make/model, serial number, site/area, installation date, warranty expiration, criticality, operational status and optional purchase cost.
- Upload attachments and maintain asset activity timeline.
- Search by asset code, name and serial; filter by site, criticality and status.
- CSV import supports preview, row-by-row error reporting and safe re-import behavior based on asset code.
- Track repair count, recorded maintenance cost and date of last service. Calculations derive from authoritative records.

### FR-03 — Corrective work orders (P0)

- Requests contain title, description, site, optional asset, requester, priority, incident timestamp and evidence attachments.
- Generate a unique organization-scoped work-order code.
- Required lifecycle: `OPEN → TRIAGED → ASSIGNED → IN_PROGRESS → AWAITING_PARTS / AWAITING_APPROVAL → IN_PROGRESS → COMPLETED → CLOSED`; separate `CANCELLED` transition with reason.
- API validates authorized transitions, required fields and a transaction-safe state change.
- Assignment records assigned technician, assigned time and reassignment history.
- Completion requires a resolution note and all mandatory checklist items; closure requires manager verification or requester acceptance, configurable per organization.
- Reopen a closed order only as a new linked follow-up order, preserving historical records.

### FR-04 — Technician execution (P0)

- 'My Work' queue sorted by priority and SLA urgency; filters for status and facility.
- Technician can start/pause work, record labor minutes, attach files, add notes, complete checklist, request parts and mark a job completed.
- Record labor as immutable time entries with correction entries rather than silently overwriting approved time.
- Technician cannot see other organizations' inventory or approve own requests.

### FR-05 — SLA engine (P0)

- Configurable response and resolution targets by priority and optionally site.
- Capture `reported_at`, `first_responded_at`, `resolved_at`, and SLA due times in UTC.
- Define response as first accepted technician action, not simply assignment. Resolution stops at `COMPLETED` and closure occurs afterward.
- Display pending, met, breached status; calculate from timestamps server-side.
- Generate in-app escalations when 80% of an SLA budget is consumed and on breach, with deduplication.
- No assumptions about business hours in MVP: SLA timers run in elapsed clock time, with the policy documented in UI.

### FR-06 — Preventive maintenance (P0)

- Templates contain name, asset category or a specific asset, checklist items, expected labor minutes, default priority and role assignment.
- Schedules support daily, weekly and monthly frequencies, a local start date, next-due date and enabled/disabled state.
- Worker generates a work order on due date and advances the next due date; enforce a unique `(schedule_id, occurrence_date)` key to prevent duplicates on restart.
- Show future schedule occurrences and overdue scheduled work.
- Editing a template updates future work only; generated orders retain snapshots of checklist details.

### FR-07 — Inventory and parts (P0)

- Store part SKU, name, unit, site-specific stock level, reorder point, unit cost and preferred supplier text.
- Every inventory change creates a ledger transaction: `RECEIPT`, `ISSUE`, `RETURN`, `ADJUSTMENT`.
- No negative stock by default. Issuing stock to a work order must be in the same database transaction as reducing balance.
- Technician requests a part; manager approves if required; stock is consumed on issue, not merely on request.
- Low-stock views and in-app alerts; no automatic purchasing or external vendor integration.

### FR-08 — Repair approvals (P0)

- Policy threshold set per organization (e.g., repair estimates over 10,000 local currency units require manager approval).
- Approval request records work order, estimated spend, justification, requester, decision, approver, timestamp and comments.
- Work cannot proceed to the approved spend-dependent action before an approval; rejected requests remain visible and auditable.
- Disallow requester self-approval and duplicate active approvals for one decision context.

### FR-09 — Dashboard and reporting (P0)

- Cards: open orders, overdue orders, completed this month, low-stock parts, response SLA compliance.
- Charts: orders by priority/status/site, maintenance spend trend, most frequently repaired assets, labor by technician.
- Compute order cost as `labor_minutes × configured hourly labor rate / 60 + sum(issued part quantity × captured unit cost)`.
- Clearly label missing cost rates as estimates/incomplete; do not silently treat unknown costs as zero.
- Include date and site filters; export filtered results to CSV; provide a printer-friendly work-order page.

### FR-10 — Notifications and audit trail (P0)

- In-app notifications for assignment, approaching SLA, breach, approval decisions and low stock.
- Unread count and read/unread state. Notifications persist across server restarts.
- Append-only audit events for create/update/delete, approvals, status changes and inventory adjustments: actor, organization, entity, action, before/after summary and timestamp.
- Audit views available to admins/managers only. No editing/removal of individual audit events from the UI.

## 6. Relational data model (minimum)

Implement migrations with appropriate PK/FK constraints, indexes and tenant isolation:

- `organizations(id, name, currency_code, timezone, approval_threshold_minor, created_at)`
- `users(id, email_normalized UNIQUE, password_hash, display_name, created_at)`
- `memberships(id, organization_id, user_id, role, active, UNIQUE(organization_id,user_id))`
- `facilities(id, organization_id, code, name, timezone, address, archived_at)`
- `areas(id, organization_id, facility_id, parent_area_id, code, name)`
- `assets(id, organization_id, facility_id, area_id, code, name, category, serial_number, criticality, status, purchased_cost_minor, warranty_expires_on, archived_at)`
- `work_orders(id, organization_id, facility_id, asset_id NULL, code, requester_id, assigned_user_id NULL, priority, status, title, description, resolution, reported_at, assigned_at, first_responded_at, completed_at, closed_at, response_due_at, resolve_due_at, parent_order_id NULL, version)`
- `work_order_events(id, organization_id, work_order_id, actor_id, from_status, to_status, note, created_at)`
- `checklist_items(id, organization_id, work_order_id, sort_order, label, required, completed_by NULL, completed_at NULL)`
- `labor_entries(id, organization_id, work_order_id, user_id, minutes_signed, rate_minor_snapshot, note, created_at)`
- `maintenance_templates(id, organization_id, name, checklist_json, estimated_minutes, default_priority, version)`
- `maintenance_schedules(id, organization_id, template_id, asset_id, frequency, start_local_date, next_local_date, enabled, timezone)`
- `schedule_occurrences(id, organization_id, schedule_id, occurrence_date, work_order_id, UNIQUE(schedule_id,occurrence_date))`
- `parts(id, organization_id, sku, name, unit, reorder_point, unit_cost_minor, UNIQUE(organization_id,sku))`
- `part_balances(id, organization_id, facility_id, part_id, on_hand_qty, UNIQUE(facility_id,part_id))`
- `stock_movements(id, organization_id, part_id, facility_id, work_order_id NULL, movement_type, quantity_signed, unit_cost_minor_snapshot, actor_id, created_at)`
- `part_requests(id, organization_id, work_order_id, part_id, requested_qty, status, requested_by, approved_by NULL)`
- `approval_requests(id, organization_id, work_order_id, requester_id, approver_id NULL, amount_minor, status, rationale, decided_at NULL)`
- `attachments(id, organization_id, entity_type, entity_id, original_name, stored_name, mime_type, size_bytes, uploaded_by)`
- `notifications(id, organization_id, user_id, type, title, body, read_at NULL, created_at)`
- `audit_logs(id, organization_id, actor_id, entity_type, entity_id, action, payload_json, created_at)`

Index all `(organization_id, status)`, `(organization_id, facility_id)`, due dates, assigned user, and audit timestamps. Use numeric minor currency units, not floating-point money. Use transactions for status and inventory changes. Consider optimistic locking (`version`) for order updates.

## 7. API contract (indicative)

- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`
- `GET/POST /api/facilities`, `GET/PATCH /api/facilities/:id`
- `GET/POST /api/assets`, `GET/PATCH /api/assets/:id`, `POST /api/assets/import`
- `GET/POST /api/work-orders`, `GET /api/work-orders/:id`, `POST /api/work-orders/:id/transition`, `POST /api/work-orders/:id/assign`
- `POST /api/work-orders/:id/labor`, `POST /api/work-orders/:id/checklist/:itemId/complete`
- `GET/POST /api/maintenance/templates`, `GET/POST /api/maintenance/schedules`, `POST /api/maintenance/run-due` (admin/dev only; idempotent)
- `GET/POST /api/parts`, `POST /api/parts/:id/movements`, `POST /api/work-orders/:id/part-requests`
- `GET /api/approvals`, `POST /api/approvals/:id/decide`
- `GET /api/reports/operations`, `GET /api/reports/export.csv`
- `GET /api/notifications`, `POST /api/notifications/:id/read`
- `GET /api/audit-logs`

Use typed request validation, predictable JSON errors `{ code, message, details? }`, pagination and non-200 errors for invalid transitions. The API must authorize object-level ownership on every read and write.

## 8. Seeded demonstration data

At least 2 organizations to demonstrate tenant isolation. Primary organization: **Riverside Hospitality**, with two properties, 3 buildings/areas per property, 120 assets, 6 technicians, 45 work orders spanning statuses, 15 inventory parts, 5 maintenance schedules and some breached SLAs. Secondary organization: **Northline Fitness**, with its own independent data. Provide named demo identities for each role and clearly marked development-only credentials in README; never ship them as production defaults.

Include specific scenarios: AC breakdown requiring a spare part, generator service scheduled for today, high-cost pump repair awaiting approval, low-stock filter, and an overdue work order.

## 11. Definition of done

- Every P0 workflow functions from UI to API to SQL and survives reload/restart.
- All roles can be exercised with seeded local accounts; unauthorized access is rejected server-side.
- Inventory and approvals preserve financial/event integrity under repeated submissions.
- At least the 15 test scenarios above run successfully, with critical domain logic unit-tested.
- The user can start the full app locally using documented commands, without Docker or internet.
- No fake buttons, static hardcoded KPI values presented as live data, broken navigation or console errors in critical paths.
- README documents known omissions, estimated versus actual costs, sandbox limitations, and basic steps to deploy later.
